# Connector: SAP Cloud ALM

SAP's delivery and operations surface for project, task, document, test,
process, analytics and go-live evidence. Used by Deploy and Run activities, and
by Explore activities that need work-item or process references.

## Packaging

This connector follows the Jira packaging pattern:

1. `server.json` contains only portable launcher wiring.
2. `scripts/start-cloud-alm-mcp.py` discovers the MCP binary and external profile.
3. `config.example.json` documents the shape without real credentials.
4. Real credentials stay outside the repository.

The launcher uses this default profile location:

```text
~/.config/sap-cloud-alm-mcp/profiles/<profile>.json
```

Override it with `MCP_CLOUD_ALM_CONFIG`. Set `MCP_CLOUD_ALM_BIN` to the
`sap-cloud-alm-mcp` executable, or install that binary on `PATH`.

Example MCP wiring generated by an adapter:

```json
{
  "cloud-alm": {
    "type": "stdio",
    "command": "python3",
    "args": [
      "./connectors/cloud-alm/scripts/start-cloud-alm-mcp.py",
      "--profile=default"
    ]
  }
}
```

## External profile

Production OAuth2 profile:

```json
{
  "tenant": "your-tenant-name",
  "region": "eu10",
  "auth_region": "eu10",
  "client_id": "your-client-id",
  "client_secret": "your-client-secret",
  "debug": false,
  "timeout_seconds": 30
}
```

Sandbox profile:

```json
{
  "sandbox": true,
  "api_key": "your-sandbox-api-key",
  "debug": false,
  "timeout_seconds": 30
}
```

Never commit a real profile. Do not put `client_secret` or `api_key` in
`server.json`, `.mcp.json`, `factory-data.json`, adapter output or logs.

## Tool posture

The upstream server exposes a broad Cloud ALM API surface, including experimental
write and delete operations. Factory activities use the following posture:

### Default read-only

Use read operations for project, task, feature, document, test, process hierarchy,
analytics, quality gate and monitoring evidence. This is the default for
discovery, design review, go-live readiness and run reporting.

### Controlled writes

Create or update operations require explicit user approval documented by the
calling skill. The skill must preview the exact payload, write the local artifact
first, perform the mutation, then re-read the Cloud ALM object and record the
result.

### Destructive operations

Delete operations and log posting are not part of the default factory posture.
They require a separately documented use case and explicit approval boundary.

## Error handling

Skills must handle and report:

- `401`: profile or token configuration problem;
- `403`: missing Cloud ALM authorization or role;
- `404`: object or endpoint not found;
- `429`: throttling; retry only where the operation is idempotent;
- `5xx`: Cloud ALM service failure; preserve the local artifact and error context.

If Cloud ALM is unavailable, the consultant must be able to continue from a
local export or manually supplied evidence and state that live synchronization
was not performed.

## Used by

- `requirements-intake` and `backlog-drafting` for work-item references;
- `cutover-planning` and `production-conversion` for Deploy evidence;
- `hypercare-triage` for Run incident context;
- `go-live-readiness` for readiness and sign-off evidence;
- `test-case-design` when test-management synchronization is explicitly enabled.

## Local verification

Without contacting Cloud ALM, verify launcher configuration with:

```bash
python3 connectors/cloud-alm/scripts/start-cloud-alm-mcp.py --help
```

For a live smoke test, use a real external profile and binary, then perform a
read-only project or task query before enabling any write operation.

## Governance contract

```yaml
data_classification:
  input: client-confidential
  output: client-confidential
  credentials: restricted
default_mode: read-only
allowed_operations: [list-projects, get-project, list-tasks, get-task, list-features, get-feature, list-documents, get-document, list-testcases, get-testcase, analytics-read]
approval_required: [create, update, create-task-comment, create-external-reference]
forbidden_operations: [delete, post-logs, production-impacting-change]
write_controls:
  preview_payload: true
  local_artifact_required: true
  reread_after_write: true
  external_id_required: true
  apply_flag_required: true
```

Cloud ALM exports and production logs remain client-confidential. Redact
personal data and secrets before sending evidence to an LLM or proposing a
reusable knowledge entry.
